# AI_CONTEXT.md — контекст проекта для ИИ-ассистента

Вставь этот файл целиком в начало диалога с любой моделью (Claude,
ChatGPT, Cursor, Copilot Chat и т.п.) перед тем, как просить её
что-то поменять в проекте. Здесь описано, что это за проект, как он
устроен, где что лежит, какие есть соглашения и на что нельзя ломать
поведение при правках.

## Что это за проект

Веб-тренажёр SQL-запросов на Flask. Пользователь видит карточку с
текстовым заданием, единую ER-схему базы данных (общую для всех
заданий) и терминал, куда вводит SQL-запрос. Запрос выполняется
по-настоящему в PostgreSQL: и эталонный запрос карточки, и запрос
пользователя запускаются в реальной БД, а их результаты (наборы строк)
сравниваются между собой — текстового сравнения строк запроса больше
нет.

Стек: Python 3, Flask, Jinja2-шаблоны, ванильный JS (без сборщиков,
без npm, без фреймворков на фронте), YAML для хранения карточек,
PostgreSQL для выполнения запросов (`psycopg2`), `python-dotenv` для
параметров подключения. Карточки по-прежнему хранятся в `*.yaml`
файлах на диске, а сама схема (`schema/database.sql`) — это уже не
просто справочный текст для ER-диаграммы, а реальный DDL+DML,
которым при старте приложения пересоздаётся учебная БД в PostgreSQL.

## Ключевые концепции

### 1. Схема БД — ОДНА на весь проект, не на карточку, и это реальный PostgreSQL

Раньше (в старой версии) у каждой карточки была своя `schema:` в
YAML, а запросы не выполнялись по-настоящему. Сейчас это НЕ ТАК.
`schema/database.sql` — это одновременно и источник текста для
ER-диаграммы, и реальный DDL+DML, которым пересоздаётся учебная БД в
PostgreSQL. Файл содержит подряд `CREATE TABLE ...` (включая
`FOREIGN KEY (col) REFERENCES table(col)`) и `INSERT INTO ...` с
тестовыми данными для всех таблиц.

Порядок инициализации при старте `app.py`:
```python
init_db()  # core/db_init.py: DROP TABLE IF EXISTS ... CASCADE для всех
           # таблиц, затем выполняет весь текст schema/database.sql
           # одним execute() — psycopg2 поддерживает несколько
           # ;-разделённых стейтментов без параметров в одном вызове
SCHEMA_TABLES = parse_schema(load_shared_schema())  # для ER-диаграммы,
SCHEMA_LINKS = flatten_links(SCHEMA_TABLES)          # как и раньше
```
1. `init_db()` выполняется один раз при старте процесса и полностью
   пересоздаёт таблицы — любые ручные правки данных через psql между
   запусками теряются.
2. `SCHEMA_TABLES`/`SCHEMA_LINKS` по-прежнему читаются один раз и не
   перечитываются на каждый запрос (для ER-диаграммы; сама БД к этому
   моменту уже пересоздана `init_db()`).
3. Параметры подключения — в `.env` (`DB_HOST`, `DB_PORT`, `DB_NAME`,
   `DB_USER`, `DB_PASSWORD`), читаются в `core/db.py` через
   `python-dotenv`. Дефолты см. в `.env.example`.
4. Карточки (`cards/*.yaml`) по-прежнему не содержат поле `schema` —
   не добавляй его обратно, если не попросили явно вернуть старое
   поведение.

Текущая схема — учебная БД "авиаперелёты":
`Company`, `Trip` (у Trip есть `company` → FK на `Company.id`),
`Passenger`, `Pass_in_trip` (FK на `Trip.id` и `Passenger.id`).

### 2. Формат карточки задания (`cards/NNN_slug.yaml`)

```yaml
id: 3
title: "Рейсы и авиакомпании"
task: |
  Для каждого рейса выведи его id и название авиакомпании,
  которая его выполняет (объедини Trip и Company).
answer: "SELECT Trip.id, Company.name FROM Trip JOIN Company ON Trip.company = Company.id;"
```

Поля: `id` (int, уникальный, генерируется автоматически при создании
через `core/card_loader.py::_next_id()`), `title` (для списка и
заголовка карточки), `task` (текст задания, многострочный через `|`),
`answer` (эталонный SQL-запрос — единственная строка, используется
только для сверки, пользователю не показывается, пока он сам не
нажмёт «Показать эталонный запрос»).

Имя файла: `{id:03d}_{slugify(title)}.yaml`, генерируется
автоматически в `save_new_card()`. Руками добавлять файлы тоже можно
— главное, чтобы `id` был уникален, имя файла на логику не влияет
(`card_loader` матчит по полю `id` внутри YAML, а не по имени файла).

### 3. Как сверяется запрос — `core/checker.py`

Текстового сравнения строк запроса больше нет. `compare_query(user_input,
answer) -> dict` выполняет ОБА запроса (эталонный и пользовательский) в
реальной PostgreSQL, сравнивает результаты и возвращает словарь:

```python
{"correct": bool, "message": str, "query": str,
 "columns": list[str], "rows": list[list]}
```

`query` — это всегда исходный `user_input` как есть. `columns`/`rows` —
результат пользовательского запроса (если он успешно выполнился), иначе
пустые списки `[]`. Этот словарь напрямую уходит в `jsonify()` в роуте
`/check` (`app.py`) — никакой отдельной сборки ответа в `app.py` нет.

1. `_execute_select(conn, query)` выполняет один запрос в своём курсоре и
   ВСЕГДА делает `conn.rollback()` в `finally` — то есть даже случайный
   `INSERT`/`UPDATE`/`DELETE` в пользовательском запросе не сохранится
   (сейчас поддерживаются только `SELECT`: если `cur.description is
   None`, значит запрос не вернул набор строк, и это трактуется как
   ошибка с понятным сообщением).
2. Если PostgreSQL бросает `psycopg2.Error` (синтаксическая ошибка,
   несуществующая колонка/таблица и т.п.) — текст ошибки (`exc.pgerror`)
   пробрасывается пользователю как есть, в `message`, а `columns`/`rows`
   остаются пустыми `[]`.
3. `_serialize_rows(rows)` приводит значения строк к JSON-сериализуемому
   виду: `str/int/float/bool/None` остаются как есть, всё остальное
   (например `datetime`/`date`/`Decimal` из `TIMESTAMP`-колонок Trip)
   приводится к `str()` — иначе `jsonify()` падает на таких типах.
4. Сравнение результатов `compare_query`:
   - названия и порядок колонок (`cur.description`) сравниваются как
     список — не совпал список → `"Названия колонок не совпадают: ..."`
     (при этом `columns`/`rows` в ответе — это уже колонки/строки
     пользовательского запроса, чтобы фронт мог показать таблицу);
   - количество строк сравнивается отдельно → `"Количество строк не
     совпадает: ..."`;
   - сами строки сравниваются как мультимножество (порядок строк не
     важен) через `sorted(rows, key=_row_sort_key)`, где
     `_row_sort_key` приводит значения к `(is_none, str(value))`, чтобы
     сортировка не падала на `NULL` и разнотипных значениях в колонке.

Если меняешь алгоритм сравнения — не убирай ROLLBACK после выполнения
пользовательского запроса, не переходи на прямое `sorted(rows)` без
устойчивого ключа (упадёт на `NULL` в колонке) и не меняй форму
возвращаемого словаря (`correct/message/query/columns/rows`) без
синхронного обновления `static/app.js::renderResult()`, который эту
форму рендерит — это осознанные решения из ТЗ.

### 4. Парсинг схемы для ER-диаграммы — `core/schema_parser.py`

`parse_schema(schema_text) -> list[dict]` — вход: сырой текст с одним
или несколькими `CREATE TABLE ... (...);`. Работает через посимвольный
подсчёт глубины скобок (`_find_matching_paren`, `_split_top_level`), а
не через одну хрупкую regex на весь блок — так корректно
обрабатываются вложенные скобки внутри `FOREIGN KEY (col) REFERENCES
table(col)` и типы вида `VARCHAR(50)`.

Возвращает список таблиц:
```python
{"name": "Trip", "columns": [{"name": "id", "type": "INTEGER", "pk": True}, ...],
 "foreign_keys": [{"column": "company", "ref_table": "Company", "ref_column": "id"}]}
```

`flatten_links(tables)` превращает `foreign_keys` каждой таблицы в
плоский список для отрисовки линий: `{"from_table", "from_col",
"to_table", "to_col"}`.

Поддерживаются: колонки с `PRIMARY KEY` (в конце определения
колонки), табличные `FOREIGN KEY (col) REFERENCES table(col)` и
инлайновые `col TYPE REFERENCES table(col)`. НЕ обрабатываются:
составные первичные ключи через отдельный `PRIMARY KEY (a, b)` (строка
просто игнорируется, ни одна колонка не получит `pk: True`) и
`ON DELETE/UPDATE ...` после `REFERENCES` (тогда `_INLINE_REF_RE` всё
равно матчит `table(col)`, но не проверяли лишние токены после — при
необходимости протестировать отдельно).

### 5. Верстка тренажёра — `templates/index.html`

Двухколоночный layout `.layout`: слева `.side-panel` (блок задания +
кнопка показа ответа + мини-список всех заданий с навигацией по
карточкам), справа `.main-panel` (текстовый редактор запроса сверху,
вкладки «Результат» / «Схема» снизу).

Вкладка «Результат» — это пустой контейнер `<div id="result">` с
плейсхолдером внутри; весь контент туда рендерит JS
(`static/app.js::renderResult(data)`) по ответу `/check`: блок с
исходным запросом (`.result-query-code`, подсвечивается через
`highlightSql()`, см. раздел 8), статус ✅/❌
(`.result-status`), HTML-таблица `columns`/`rows`, если они есть
(`.result-table`), и текст `message` (`.result-message`). В шаблоне
жёсткой разметки под это нет — если меняешь форму ответа `/check` в
`core/checker.py`, обнови `renderResult()` синхронно, иначе фронт
покажет пусто или сломается на `undefined`.

Вкладка «Схема» рендерит `schema_tables` (из Flask-контекста) как
карточки таблиц (`.schema-table`), а связи (`schema_links`, embedded
как JSON в `<script type="application/json" id="schemaLinksData">`)
дорисовываются JS-ом поверх SVG (`static/app.js::drawSchemaDiagram`) —
линии считаются по `getBoundingClientRect()` DOM-элементов колонок
(`id="schema-col-{table}-{column}"`), поэтому таблицы/колонки должны
сохранять этот паттерн id, если трогаешь верстку.

Клик по схеме вставляет название в терминал. У каждой `.schema-table`
есть `data-table="{имя}"`, у каждой `.schema-col` — `data-table`,
`data-column` и `data-type` (их рисует Jinja в `index.html`). В
`static/app.js` (рядом с редактором запроса, сразу после первого
`syncEditor()`) на `#schemaDiagram` висит один делегированный
обработчик `click`:

- клик по колонке (`.schema-col`) вставляет **только имя колонки**
  (`col.dataset.column`, например `company`) — без префикса таблицы;
  префикс `Таблица.` пользователь явно отверг;
- клик по заголовку/телу таблицы вставляет имя таблицы
  (`table.dataset.table`, например `Trip`).

Вставка делает `insertIntoQuery(text)`: пишет в позицию курсора
`#queryInput` (`selectionStart`/`selectionEnd`; выделенный текст
заменяется), перед текстом ставит пробел, если слева есть символ и это
не пробел, `(` или `,`, затем возвращает фокус в textarea, ставит
курсор после вставки и вызывает `syncEditor()` — без этого слой
подсветки (раздел 8) не обновится, потому что программная смена
`input.value` не шлёт событие `input`. Если в `JOIN` имя колонки
неоднозначно (`id` в двух таблицах), PostgreSQL вернёт ошибку, и
пользователь дописывает таблицу вручную — это осознанное поведение.
Никаких серверных роутов, `core/*` и Docker-настроек это не касается.
Стили — только курсор `pointer` и hover у `.schema-table-title` и
`.schema-col` в `style.css` (через переменные, цвета не хардкодятся).
Если меняешь верстку схемы, сохрани `data-*`-атрибуты — на них
держится вставка.

Важно: диаграмма перерисовывается только когда вкладка «Схема»
активна (`requestAnimationFrame(drawSchemaDiagram)` в
`activateTab()`) и по `resize`, если эта вкладка открыта — потому что
у скрытых (`hidden`) элементов нулевые размеры, посчитать линии для
них нельзя.

### 6. Дизайн-токены — `static/style.css`, секция `:root`

Тёмная тема: `--bg #0e1116`, `--panel #171b24`, `--accent #e0a458`

### 8. Подсветка SQL и настройки цветов — `static/app.js`, `static/style.css`, `templates/base.html`

Подсветка целиком клиентская: ни `app.py`, ни `core/*`, ни Docker для
неё не менялись. Серверных роутов и хранения цветов на сервере нет —
цвета лежат в `localStorage` браузера (ключ `sqlTrainer.hlColors`),
потому что проект локальный, а Postgres/файлы в контейнере пересоздаются.

**Где что лежит.** `static/app.js` — один IIFE из трёх частей, в таком
порядке:
1. Ядро подсветки между маркерами `// <hl-core>` и `// </hl-core>`:
   списки слов, `TOKEN_RE`, `classifyWord()`, `highlightSql(text)`.
   Ядро не трогает DOM (маркеры нужны, чтобы вырезать его и тестировать
   в Node, не поднимая браузер).
2. Настройки: `HL_GROUPS` (категории и подписи), `PREVIEW_SQL`,
   `initSettings()` — строит список цветов в окне `#settingsPanel`,
   читает/пишет `localStorage`, ставит переменные на `<html>`.
3. Тренажёр (`const layout = document.querySelector(".layout"); if
   (!layout) return;`) — после этого `return` код выполняется только на
   странице карточки.

`app.js` подключается из `templates/base.html` на ВСЕХ страницах (чтобы
кнопка «⚙ Настройки» работала везде). Не подключай его снова в
`index.html` — обработчики повесятся дважды.

**Как работает `highlightSql(text)`.** Один проход регулярным
выражением `TOKEN_RE` слева направо, возвращает безопасный HTML (весь
текст проходит через `escapeHtml`) со `<span class="hl-КАТЕГОРИЯ">`.
Порядок альтернатив в `TOKEN_RE` важен: комментарии (`--`, `/* */`)
раньше операторов, иначе `--` распадётся на два минуса. Слово
классифицирует `classifyWord()` по приоритету:
1. слово после `.` (`t.date`, `Trip.class`) → `ident` (всегда имя);
2. имя функции И следующий непробельный символ `(` → группа функции
   (поэтому `LEFT JOIN` — ключевое слово, а `LEFT(name, 3)` — функция);
3. `current_date`, `localtime`, `current_user` и т.п. → функция и без
   скобок (`NO_PAREN_WORDS`);
4. `null/true/false` → `const`; 5. типы → `type`; 6. ключевые слова →
   `keyword`; 7. всё остальное → `ident`.

Для поиска слов используются `Map`/`Set`, а не обычные объекты:
колонка с именем `constructor` или `toString` не должна совпасть со
свойством прототипа.

**Категории (CSS-классы `hl-*` и переменные `--hl-*`):** `keyword`,
`type`, `ident`, `operator`, `punct`, `string`, `number`, `const`,
`comment`, и функции: `fn-agg` (агрегатные), `fn-str` (строковые),
`fn-date` (дата/время), `fn-math` (математические), `fn-win` (оконные),
`fn-other` (прочие).

**Цвета: единый источник — CSS.** Стандартные значения заданы в
`style.css` в `:root` как `--hl-<категория>: #rrggbb`. JS НЕ хранит
дефолты: `initSettings()` читает их через `getComputedStyle` до
применения пользовательских, и использует для кнопок сброса. Поэтому:
- значения в `:root` — только 6-значный hex (`<input type="color">`
  другого не принимает; иначе дефолт упадёт в `#cccccc`);
- пользовательский цвет = inline-свойство `--hl-<id>` на `<html>`;
  «сброс» = `removeProperty`, и снова виден дефолт из CSS;
- в `localStorage` хранятся только цвета, отличающиеся от дефолта
  (`{"keyword": "#ff0000"}`); при сбросе всех ключ удаляется.

**Редактор запроса.** `#queryInput` (`<textarea>`) на странице
оборачивается JS-ом в `.terminal-editor`, под ним создаётся
`<pre class="terminal-highlight" aria-hidden>`; на каждый `input`
`syncEditor()` кладёт в `<pre>` подсвеченный HTML и растягивает
textarea по высоте контента. Текст самой textarea прозрачный, виден
только слой под ней и каретка. Инварианты, без которых слои
разъедутся:
- у `.terminal-input` и `.terminal-highlight` ОДИНАКОВЫЕ
  шрифт/размер/`line-height`/`padding`/`white-space`/`overflow-wrap`/
  `tab-size` (общее правило в `style.css`) — меняй их только вместе;
- `line-height` задан явно в обоих (у textarea по умолчанию `normal`,
  у `<pre>` он наследуется от body);
- textarea авто-растёт (`overflow: hidden`, `resize: none`), чтобы не
  появлялась полоса прокрутки и перенос строк в слоях совпадал; не
  возвращай `resize: vertical` без синхронизации прокрутки;
- `color: transparent` у textarea действует только в селекторе
  `.terminal-editor .terminal-input` — без JS (нет обёртки) запрос
  остаётся читаемым; не переноси это правило на `.terminal-input`;
- если запрос кончается переводом строки, в `<pre>` добавляется пробел,
  иначе последняя пустая строка схлопывается.

**Остальные места подсветки:** `#answerReveal` (эталон) получает
`innerHTML = highlightSql(textContent)` при загрузке; в `renderResult()`
блок `.result-query-code` рендерится через `highlightSql(data.query)`
(вместо прежнего `escapeHtml`).

**Окно «Настройки».** Разметка в `base.html` (`#settings`,
`#settingsBtn`, `#settingsPanel`, `#hlPreview`, `#hlList`,
`#hlResetAll`), строки с пикерами генерирует `initSettings()` из
`HL_GROUPS`. Закрывается по клику вне окна и `Esc`.

**Типовые правки:**

| Что нужно | Что менять |
|-----------|-----------|
| Добавить функцию PostgreSQL | слово (строчными) в нужную группу в `FUNCTION_WORDS` |
| Добавить ключевое слово / тип | в `KEYWORDS` / `TYPES` |
| Функция без скобок (как `CURRENT_DATE`) | дополнительно в `NO_PAREN_WORDS` |
| Новая категория токена | 1) `--hl-<id>` в `:root`; 2) правило `.hl-<id>` в `style.css`; 3) строка в `HL_GROUPS` в `app.js`; 4) вернуть `<id>` из `classifyWord()`/`highlightSql()` |
| Поменять палитру по умолчанию | только `--hl-*` в `:root` (hex на 6 знаков) |
| Подсветка в другом поле (например форма карточки) | повторить схему «textarea + слой» с теми же метриками, либо подсвечивать `<pre>` через `highlightSql()` |

**Что не поддерживается (упрощения):** вложенные блочные комментарии
`/* /* */ */`, строки `E'...'`, параметры `$1`, `:name`. Тип-слова
(`date`, `time`, `text`) красятся как типы и в роли имён колонок.

**Как проверять.** Браузера в окружении может не быть. Ядро
тестируется в Node: вырезать текст между `// <hl-core>` и
`// </hl-core>`, вычислить через `new Function(core + "; return
highlightSql;")()` и прогнать запросы. Полезные проверки: `LEFT JOIN`
vs `LEFT(name,3)`, `t.date`, `'it''s'`, незакрытые `'` и `/*`, `a<b`
(экранирование `<`), и что «удалить теги → исходный текст» даёт ровно
исходник. Страницу целиком можно прогнать через `jsdom`
(отрендерить Jinja-шаблон, выполнить `app.js`, проверить, что слой
подсветки и 15 строк настроек создались).

## Правила при внесении изменений

1. Схема БД одна на все задания — не возвращай `schema:` в карточки,
   если явно не попросили откатить это решение.
2. `core/*.py` не импортирует Flask и ничего не знает про HTTP —
   держи бизнес-логику отделённой от `app.py`, если добавляешь новые
   функции. `core/db.py`/`core/db_init.py` — исключение в том смысле,
   что они знают про psycopg2/PostgreSQL, но всё равно не про Flask.
2a. Пользовательский SQL выполняется по-настоящему — при доработке
    `checker.py` не убирай `ROLLBACK` после каждого запроса и не
    разрешай нечего кроме `SELECT`, если явно не попросили обратное
    (иначе через тренажёр можно менять данные в БД).
3. Все цвета/шрифты — через CSS-переменные из `:root`, не хардкодь.
4. JS — один файл `static/app.js`, один IIFE, без внешних библиотек и
   без ES-модулей (проект не использует сборщик). Файл подключается
   в `base.html`, а не в отдельных шаблонах.
4a. Подсветка SQL: дефолтные цвета только в `style.css` (`--hl-*`,
    6-значный hex), JS их не дублирует; HTML от `highlightSql()`
    безопасен только потому, что внутри все токены экранируются — не
    вставляй в `innerHTML` пользовательский текст в обход неё;
    метрики шрифта у `.terminal-input` и `.terminal-highlight` держи
    одинаковыми (раздел 8).
4b. Клик по схеме (раздел 5): вставляй в терминал только имя колонки
    или таблицы, без `Таблица.` перед колонкой; после программной
    записи в `#queryInput.value` всегда вызывай `syncEditor()`;
    `data-table`/`data-column`/`data-type` в `index.html` не убирай.
5. Если меняешь формат карточки или схемы — обнови и `README.md`, и
   этот файл, и существующие карточки/схему под новый формат, чтобы
   всё осталось консистентным.
6. Перед тем как что-то менять в `core/checker.py`, `core/schema_parser.py`
   или файлах в `cards/`/`schema/` — прогони sanity-check через Flask
   test client (`app.test_client()`), а не только глазами по коду:
   реальные баги в этом проекте чаще всего в regex/парсинге границ.
